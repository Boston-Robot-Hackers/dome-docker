# Chores

- [x] Fix `scripts/dome-config.sh` resolving `manifest/` one level above the repo root when `source`d from zsh — `${BASH_SOURCE[0]}` isn't reliably populated by zsh on plain `source`, so `dirname` fell back to cwd (repo root) and `../manifest` landed a level too high (`ERROR: 'DOME_USER' not set in .../dome-docker/../manifest/config.txt`). Switched to resolving `manifest/` from `$(pwd)` (matches the already-documented "cd to repo root first" usage) with a clear error if `manifest/config.txt` isn't found there. Regression test: `tests/test_f01_manifest.sh` "dome-config.sh sourced under zsh" check.
- [x] `scripts/host-setup.sh` now prints the target's global IPv4 addresses (`ip -4 -o addr show scope global`) just before finishing, so VM users (where `dome.local` mDNS often doesn't resolve) don't have to find the IP themselves some other way. Updated `02-doc/shell-howto.md` and `02-doc/docker-howto.md` "SSH back in" steps to reference this output instead of telling the user to look the IP up externally. No automated test — `ip` is Linux-only (the script only ever runs on the Pi/VM target, never on the Mac dev machine), so this is manual/visual verification during T10 (real VM/Pi bring-up).
- [x] Fix `scripts/host-setup.sh` resolving `DOME_USER` as `root` — it only read the `DOME_USER` env var (`USERNAME="${DOME_USER:-${USER:-robot}}"`), never `manifest/user.txt`, but the documented workflow never exports `DOME_USER`, only writes it into `manifest/user.txt`. Under `sudo`, `$USER` is `root`, so `DOME_DIR=/home/root/dome-docker` was wrong and `grep: /home/root/dome-docker/manifest/user.txt: No such file or directory` followed (hit live during VM bring-up). Fixed to read `manifest/user.txt` then `manifest/config.txt` default, same env > user.txt > config precedence as `bare-metal-build.sh`/`dome-config.sh`. Verified by resolving against the real manifest files (got `pitosalas`, not `root`). No automated test — same Linux-only constraint as the IP-printing chore above.
- [x] Remove bogus `dome-docker` entry from `manifest/packages.txt` `[ros]` section — introduced in commit `e158702` with no stated rationale, it made `bare-metal-base.sh` apt-install a nonexistent `ros-kilted-dome-docker` package, failing live during VM bring-up (`E: Unable to locate package ros-kilted-dome-docker`). Not a real ROS package, just the repo's own name accidentally left in the list. Regression test: `tests/test_f01_manifest.sh` "packages.txt [ros] has no bogus self-referential entry" check.
- [x] Removed time estimates ("10-30 min", "20-60 min", "10-15 min") from `02-doc/shell-howto.md`/`docker-howto.md`/`README.md` per explicit user feedback — durations vary too much across Pi/VM/network to be meaningful, and a wrong number is worse than none.
- [x] Fix `manifest/bashrc` sourcing `~/rosutils/ros2_robot_bashrc.bash` without exporting `ROS_DISTRO` first — that script requires it set and errors (`ROS_DISTRO: ERROR: ROS_DISTRO must be set before sourcing ros2_robot_bashrc.bash`, `bash: /opt/ros//setup.bash: No such file or directory`), hit live in a new terminal after `bare-metal-build.sh`. Fixed by exporting `ROS_DISTRO` from `~/dome-docker/manifest/config.txt` as the first line of `bashrc`, before the `source`. Regression test: `tests/test_f01_manifest.sh` "bashrc exports ROS_DISTRO before sourcing rosutils" check (verifies export precedes the source line).
- [x] Added VS Code (`[vscode]` section, Microsoft's official apt repo) to `manifest/apt-repos.txt`, same pattern as `doppler`/`github-cli`. Target is Ubuntu Desktop (not headless Server, per user — that's the ISO actually used for the VM scenario), so a GUI editor is applicable. Universal (not `DOME_TARGET`-gated) — apt-installing `code` is harmless on a headless target even if there's no GUI to run it. Updated `README.md`/`02-doc/notes.md`/`02-doc/spec.md`/`02-doc/shell-howto.md` mentions of the apt-repos.txt third-party list; added `vscode` to the `test_f01_manifest.sh` apt-repos.txt section-field loop.
